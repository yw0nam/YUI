# YUI — Backend Integration

Chat io has three protocol modes, selected by `chat_api` in `configs/endpoints.json`: `responses`, described below, routes to the selected backend over the OpenAI Responses API and carries the full `generate_express` expression contract. `chat_completions` (the shipped default) connects over the OpenAI-compatible Chat Completions API; the client declares `generate_express` itself with the vocabulary baked into the tool schema, runs the call locally, and returns the result over up to three round trips. Backend capability differs by provider: a plain OpenAI-compatible server (e.g. vLLM) speaks standard Chat Completions tool-call streaming; requirements specific to Hermes Agent live in [integrations/hermes/README.md](../../integrations/hermes/README.md). (`chat_completions` mode also threads the conversation transcript locally instead of via `previous_response_id`.) `push` keeps one WebSocket open to the backend instead of making a call per turn: the client sends the turn on it and the backend sends a finished reply on it, so a reply can arrive with no turn behind it. Every frame is specified in [docs/reference/push-transport.md](../reference/push-transport.md). In push mode the client shows the backend's `delegations` list in two places: a chip beside the avatar — a pulsing dot with the running count, tappable to open the list, long-pressable to fold to the dot — and, in the settings panel's Session section, the persisted history of every item the client has seen, each finished row opening its summary. The client computes each row's elapsed and "ago" text from the list's `started_at`/`ended_at` stamps and renders what the backend sends; a `done` item leaves the chip 30 minutes after `ended_at` and stays in the Session section until the history cap evicts it. The rest of this doc covers `responses` mode.

Chat, STT and TTS use the **OpenAI-compatible API**; the broker is an MCP. Separate processes, all swappable via config:

- **chat → selected backend** `chat_base_url` + `/responses` or `/chat/completions` per `chat_api`, or a WebSocket to `<chat_base_url>/ws` in push mode
- **STT →** `stt_base_url` (includes `/v1`, e.g. `localhost:5517/v1`) + `/audio/transcriptions`, with `model` from `stt_model` when set
- **TTS →** `tts_base_url` (`localhost:8088`) `/v1/audio/speech`, with `model` from `tts_model` and `voice` from the speaker selected in the panel. `tts_provider` (`irodori` default, `openai`) shapes the request and the voice list: Irodori prepends `emotion_text` to `input` and sends `caption` as `irodori.caption`; OpenAI sends plain `input` with `emotion_text` and `caption` joined into `instructions`. OpenAI's speakers are its 13 built-in voices, and import, delete, and re-upload are off. Irodori's speakers are listed by `GET {tts_base_url}/v1/audio/voices` — YUI carries no bundled catalog — plus any clip the user imports, which is uploaded to `POST`/`PUT /v1/audio/voices` and removed with `DELETE /v1/audio/voices/{voice_id}`. An imported voice's `voice_id` is ASCII (`[A-Za-z0-9_-]`), derived from the name typed at import, and the panel label keeps that name as free text; at startup a user voice persisted under any other id moves to its ASCII id, or gives way to a re-import that already holds that id, before the voice list refresh re-uploads it
- **Expression Broker** (config-driven) `broker_base_url` (`localhost:3201/mcp`, streamable-http MCP) — YUI publishes renderable emotion/motion/emotion_text vocabulary, the agent reads it (publish skipped if unset)

**Auth.** Each call carries `Authorization: Bearer` from a key resolved through `SecretProvider` — a runtime settings override (the Connection tab's key store), else, in dev builds only, the `.env.local` fallback: chat `VITE_YUI_CHAT_KEY`, STT `VITE_YUI_STT_KEY`, TTS `VITE_YUI_TTS_KEY`. Release builds read only the key store. An empty key sends no header.

**Deadlines.** TTS synthesis, STT transcription and the voices API (list, upload, delete) each settle within a fixed deadline; a request past its deadline rejects as a timeout. In the Tauri app the fetch transport cannot cancel a body read in flight, so the client races the body read against the same deadline and the request settles even when the server stalls mid-body.

**Control signals** are delivered as server-side `generate_express` tool-calls in the `/v1/responses` stream. Arguments are flat: `{ emotion_id?, motion_id?, emotion_text?, caption? }`; `emotion_text` is a TTS voice tag, drawn from the emoji set the Expression Broker publishes when `tts_provider` is `irodori` and free text otherwise, which the agent learns via the broker, and `caption` is free-text voice direction carried beside the spoken text in the audio request. Speech text is a separate assistant text stream (`response.output_text.delta`). `function_call` items are excluded from final `output[]` — must be captured during streaming. The renderable emotion/motion vocabulary is brokered by the Expression Broker MCP; the `generate_express` cue contract handed to the backend agent lives in [`docs/reference/client-context.md`](../reference/client-context.md).
