# YUI — Backend Integration

Chat io has three protocol modes, selected by `chat_api` in `configs/endpoints.json`: `responses`, described below, routes to the selected backend over the OpenAI Responses API and carries the full `generate_express` expression contract. `chat_completions` (the shipped default) connects over the OpenAI-compatible Chat Completions API. On both, the client declares `generate_express` itself with the vocabulary baked into the tool schema, runs the call locally, and returns the result over up to three round trips (the Responses follow-up re-sends the input items, so the in-turn round trip does not depend on the server keeping the earlier response; across turns Responses chains on `previous_response_id`, and a 404 for the stored id resets the chain with one retry). Backend capability differs by provider: a plain OpenAI-compatible server (e.g. vLLM) speaks standard Chat Completions tool-call streaming; requirements specific to Hermes Agent live in [integrations/hermes/README.md](../../integrations/hermes/README.md). (`chat_completions` mode also threads the conversation transcript locally instead of via `previous_response_id`.) `push` keeps one WebSocket open to the backend instead of making a call per turn: the client sends the turn on it and the backend sends a finished reply on it, so a reply can arrive with no turn behind it. Every frame is specified in [docs/reference/push-transport.md](../reference/push-transport.md). In push mode the client shows the backend's `delegations` list in two places: a chip beside the avatar — a pulsing dot with the running count, tappable to open the list, long-pressable to fold to the dot — and, in the settings panel's Session section, the persisted history of every item the client has seen, each finished row opening its summary. The client computes each row's elapsed and "ago" text from the list's `started_at`/`ended_at` stamps and renders what the backend sends; a `done` item leaves the chip 30 minutes after `ended_at` and stays in the Session section until the history cap evicts it. The modes differ in who keeps the conversation history: the client on `chat_completions`, the server on `responses`, the backend on `push`; currently only [Hermes Agent](https://github.com/NousResearch/hermes-agent) supports `push`. The rest of this doc covers `responses` mode.

Chat, STT and TTS use the **OpenAI-compatible API**. Separate processes, all swappable via config:

- **chat → selected backend** `chat_base_url` + `/responses` or `/chat/completions` per `chat_api`, or a WebSocket to `<chat_base_url>/ws` in push mode
- **STT →** `stt_base_url` (includes `/v1`, e.g. `localhost:5517/v1`) + `/audio/transcriptions`, with `model` from `stt_model` and `language` from `stt_language` when set (`auto` omits `language`)
- **TTS →** `tts_base_url` (`localhost:8088`) `/v1/audio/speech`, with `model` from `tts_model` and `voice` from the speaker selected in the panel. `tts_provider` (`irodori` default, `openai`, `fish`) shapes the request and the voice list: Irodori prepends `emotion_text` to `input` and sends `caption` as `irodori.caption`; OpenAI sends plain `input` with `emotion_text` and `caption` joined into `instructions`; Fish posts `/v1/tts` with `text` led by each cue in its own `[...]` pair. Whatever the provider, the device-wide reading dictionary has already rewritten the sentence. OpenAI's speakers are its 13 built-in voices, and import, delete, and re-upload are off. Irodori's speakers are listed by `GET {tts_base_url}/v1/audio/voices` — YUI carries no bundled catalog — plus any clip the user imports, which is uploaded to `POST`/`PUT /v1/audio/voices` and removed with `DELETE /v1/audio/voices/{voice_id}`. An imported voice's `voice_id` is ASCII (`[A-Za-z0-9_-]`), derived from the name typed at import, and the panel label keeps that name as free text; at startup a user voice persisted under any other id moves to its ASCII id, or gives way to a re-import that already holds that id, before the voice list refresh re-uploads it

**Auth.** Each call carries `Authorization: Bearer` from a key resolved through `SecretProvider` — a runtime settings override (the settings window's key fields: chat and TTS on the Connection page, STT on the Listening page), else, in dev builds only, the `.env.local` fallback: chat `VITE_YUI_CHAT_KEY`, STT `VITE_YUI_STT_KEY`, TTS `VITE_YUI_TTS_KEY`. Release builds read only the key store. An empty key sends no header.

**Deadlines.** TTS synthesis, STT transcription and the voices API (list, upload, delete) each settle within a fixed deadline; a request past its deadline rejects as a timeout. In the Tauri app the fetch transport cannot cancel a body read in flight, so the client races the body read against the same deadline and the request settles even when the server stalls mid-body.

**Control signals** arrive as exact `generate_express` tool calls in the Responses stream. The client declares the tool, runs it locally, and answers it. Arguments are flat: `{ emotion_id?, motion_id?, emotion_text?, caption? }`. The tool schema carries the renderable emotion/motion vocabulary and the Irodori emoji table; other TTS providers use free text for `emotion_text`. `caption` is free-text voice direction. Speech arrives separately in `response.output_text.delta`; function calls are captured during streaming. The cue contract lives in [`client-context.md`](../reference/client-context.md).

On Hermes, expression cues arrive on the push transport only; Chat Completions and Responses carry none, because the Hermes API server does not pass a request's tools to its model.
