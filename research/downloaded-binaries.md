# Running a downloaded plugin binary on macOS and Windows (issue #1659)

Research date: 2026-10-28. Repo checkout: `YUI-research-binaries` at commit `a4eb13fa`.

## Summary

The checkout has no plugin download, unzip, or spawn code. The only child process it starts is the externally installed `ego-browser` CLI (`src-tauri/src/browser/relay.rs:97,127`; located by `src-tauri/src/browser/locate.rs`). So every answer below is about a feature that does not exist yet. On macOS, the primary sources say the quarantine xattr is driven by the `LSFileQuarantineEnabled` key and that Gatekeeper's user-approval step applies to downloaded software. They do not say whether a Rust HTTP writer's files get quarantined; that needs a measurement on a signed build. Apple's notarization doc requires Developer ID signing, the hardened runtime, and notarization for software distributed outside the App Store, and says apps can load quarantined plug-ins only if they are notarized. The hardened-runtime exceptions (`allow-jit`, `allow-unsigned-executable-memory`, `disable-library-validation`) govern YUI's own process, not a spawned child, so the child should carry its own signature and no extra entitlement. Do not clear quarantine: no primary source endorses it, and it would defeat the first-open approval. On Windows, SmartScreen reputation covers files an app downloads and runs, and a valid signature is one input to reputation; the repo's Windows bundles are unsigned. The recommendation is to Developer-ID sign and notarize the macOS plugin binaries, Authenticode-sign the Windows ones, and show a clear fallback message when the OS blocks a binary.

## macOS

### Q1. Does quarantine apply to files YUI writes itself?

- **Primary (Apple):** the `LSFileQuarantineEnabled` Info.plist key is documented as "A Boolean value indicating whether the files this app creates are quarantined by default." ([Apple JSON for the key](https://developer.apple.com/tutorials/data/documentation/bundleresources/information-property-list/lsfilequarantineenabled.json)).
- **Secondary (not from Apple):** Zscaler's Gatekeeper write-up and Eclectic Light say an app opts in to File Quarantine through this key, and that the attribute is then applied to files it creates ([Zscaler](https://www.zscaler.com/jp/blogs/cybersecurity-best-practices/gatekeeper); [Eclectic Light, "Who decides to quarantine files?"](https://eclecticlight.co/2025/12/08/who-decides-to-quarantine-files/)). Eclectic Light also describes a system exceptions list that can override the key. An Apple Developer Forums thread reports that setting the key to NO did not clear the flag on files written by a File Provider extension ([forum thread 701687](https://developer.apple.com/forums/thread/701687)). Treat all of this as secondary.
- **Reqwest vs NSURLSession / browser:** no primary source says a Rust HTTP client's writes are or are not quarantined. The browser path is the best-documented one: browsers and the system mark downloads. The answer for YUI depends on its Info.plist, which currently sets only `NSMicrophoneUsageDescription` (`src-tauri/Info.plist:5-6`). It sets no `LSFileQuarantineEnabled` key. **UNVERIFIED by test:** run a release build that writes a file, then `xattr -l` the file.
- **Zip extraction:** whether a file extracted from a quarantined zip inherits the xattr depends on the extractor (for example Archive Utility). No primary source found. UNVERIFIED.

### What quarantine gates

- Apple's support article describes the mechanism: "Before you open a downloaded app for the first time, macOS asks for your approval" ([Apple, Safely open apps on your Mac](https://support.apple.com/en-us/102445)).
- Apple's Platform Security Gatekeeper page says the first-open check applies "regardless of how it arrived on the Mac," and that Gatekeeper "requests user approval before opening downloaded software for the first time." It does not name `com.apple.quarantine`, and it does not address command-line tools, shell-launched binaries, or child processes ([Apple Platform Security, Gatekeeper and runtime protection](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web)).
- So: the approval prompt is tied to downloaded software. A bare binary exec'd by YUI with `posix_spawn`/`Command` does not go through the LaunchServices open path that shows the prompt. This is an inference from the silence above, not a documented fact. **UNVERIFIED.**
- **Unsigned binary run without a prompt:** on Apple silicon, secondary sources (quoting Apple release notes) say the kernel requires every executable to carry a valid signature, and an ad hoc signature is enough to run ([Eclectic Light, "Apple Silicon Macs will require signed code"](https://eclecticlight.co/2020/08/22/apple-silicon-macs-will-require-signed-code/)). A secondary search summary also says ad hoc signatures carry no identity and cannot pass Gatekeeper (no single page confirmed this wording; see [Eclectic Light, "How Monterey checks apps and executable code"](https://eclecticlight.co/2022/03/04/how-monterey-checks-apps-and-executable-code/) for the related checks). **UNVERIFIED against Apple primary text.** On Intel, the same sources say the rule does not apply.

### Q2. Must the plugin binary be signed or notarized by its author?

- Apple's notarization doc: "Beginning in macOS 10.15, all software built after June 1, 2019, and distributed with Developer ID must be notarized." It requires a Developer ID certificate (not ad hoc), the Hardened Runtime, and a secure timestamp ([Apple, Notarizing macOS software before distribution, JSON](https://developer.apple.com/tutorials/data/documentation/security/notarizing-macos-software-before-distribution.json)).
- On plug-ins: "In macOS 10.15 and later, apps can load quarantined plug-ins — those downloaded from the internet or transferred with AirDrop — only if the plug-in is notarized. For plug-ins that aren't notarized, the user must explicitly approve the plug-in" (same source). This is about in-process plug-ins, not a spawned child, but it is the closest primary statement to "downloaded code runs".
- Apple's hardened-runtime text: "You add entitlements only to executables. Shared libraries, frameworks, and in-process plug-ins inherit the entitlements of their host executable" ([Apple, Hardened Runtime, JSON](https://developer.apple.com/tutorials/data/documentation/security/hardened-runtime.json)). A child executable is its own executable with its own entitlements, so the parent's entitlements do not transfer to it.
- **Library validation and child exec:** Apple's description of `com.apple.security.cs.disable-library-validation` is "A Boolean value that indicates whether the app loads arbitrary plug-ins or frameworks, without requiring code signing" ([Apple, Hardened Runtime, JSON](https://developer.apple.com/tutorials/data/documentation/security/hardened-runtime.json)). That governs libraries loaded into the process. Whether the parent's hardened runtime checks a spawned child's signature at exec time: **no primary source found. UNVERIFIED.** The kernel's arm64 signature requirement (above) applies to the child regardless of the parent's runtime flags, per secondary sources.
- **JIT / unsigned executable memory:** the entitlements are described as letting "the app" create writable and executable memory (`allow-jit`, `allow-unsigned-executable-memory`) ([Apple, Hardened Runtime, JSON](https://developer.apple.com/tutorials/data/documentation/security/hardened-runtime.json)). These apply to YUI's own process. A child that needs JIT (for example a Node or Python runtime) needs its own entitlements in its own signature. UNVERIFIED for specific runtimes.
- **Process/posix_spawn of a file inside app data:** no primary Apple statement. The App Sandbox is not in use (`src-tauri/Entitlements.plist` has no `com.apple.security.app-sandbox` key), so no sandbox inheritance question arises today.

### Q3. May YUI clear quarantine (`xattr -d com.apple.quarantine`)?

- No Apple primary statement found either way. **UNVERIFIED.**
- Vendor precedent (documented user step, not an app behavior): VS Code's smoke-test README tells a macOS user to run `xattr -d com.apple.quarantine <path to server with web folder zip>` before unzipping, "to avoid security issues on startup" ([microsoft/vscode, test/smoke/README.md:46-51](https://github.com/microsoft/vscode/blob/main/test/smoke/README.md)).
- Judgment (not a source): if the plugin was downloaded through YUI with the xattr set, clearing it removes the first-open approval Apple describes. That is a Gatekeeper bypass, not a repair. If YUI's writer does not set the xattr, there is nothing to clear. Do not add a clear step.

## Windows

### Q4. SmartScreen, Mark of the Web, and unsigned EXEs

- **SmartScreen covers downloaded programs and reputation.** Microsoft's SmartScreen overview says it "checks downloaded files against a list of files that are well known and downloaded frequently. If the file isn't on that list, Microsoft Defender SmartScreen shows a warning." It also states "It also provides reputation checks for apps, checking downloaded programs and the digital signature used to sign a file. If a URL, a file, an app, or a certificate has an established reputation, users don't see any warnings. If there's no reputation, the item is marked as a higher risk and presents a warning to the user." It further says it "checks any files an app (including 3rd-party browsers and email clients) that attempts to download and run" ([Microsoft Learn, Microsoft Defender SmartScreen overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/)).
  - Implication: a valid signature is an input to reputation. YUI's download-and-run of a plugin matches "any files an app ... attempts to download and run" as written. Whether a file YUI writes via HTTP actually gets the MOTW that SmartScreen keys on is **UNVERIFIED** (see below).
- **Mark of the Web / Zone.Identifier (secondary only):** search results (security blogs, not Microsoft) say the MOTW is a `Zone.Identifier` alternate data stream with ZoneId 3 for the Internet zone. They say browsers and mail clients write it, and that apps write it either directly or through `IAttachmentExecute`. They also say coverage is not universal ([textslashplain, Downloads and the Mark of the Web](https://textslashplain.com/2016/04/04/downloads-and-the-mark-of-the-web); [Outflank](https://www.outflank.nl/?p=1371)). The Microsoft Learn MOTW and Attachment Execution Services pages were not reachable in this session, so: **UNVERIFIED against Microsoft primary text** for who sets it and whether an app's own HTTP write gets it.
- **Unsigned EXE from app data:** SmartScreen's no-reputation warning (above) is the documented behavior for an unrecognized download-and-run. Whether this specific path (a child process of a non-MOTW file) triggers a prompt: **UNVERIFIED.**
- **AppLocker / WDAC:** not verified. No primary source fetched. **UNVERIFIED.** Enterprise policies can block unsigned executables, but whether YUI's app-data path is covered depends on policy configuration, not on the file origin.
- **Repo (Windows):** `.github/workflows/release.yml:100-103` is the Windows matrix entry with no signing step. The only signing step is the macOS-gated `Export Apple signing credentials` step (`release.yml:123`, `if: runner.os == 'macOS'`). There is no Windows certificate secret or Authenticode step in the workflow. The MSI and NSIS installers are unsigned.

## What other hosts do

### MCPB (Claude Desktop MCP Bundles)

- Native binaries: `server.type = "binary"` means "Pre-compiled executable with all dependencies included", and "Platform-specific binaries supported" ([modelcontextprotocol/mcpb, MANIFEST.md:446-462](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md)). Compatibility lists `platforms` as `darwin`, `win32`, `linux` (MANIFEST.md:333). `platform_overrides` selects per-platform config (MANIFEST.md:503-511).
- Signing: `mcpb sign` signs the `.mcpb` file itself with a PEM certificate (PKCS#7). It is a bundle-level signature, not Apple codesign or Authenticode for the embedded binary ([mcpb CLI.md:92-115](https://github.com/modelcontextprotocol/mcpb/blob/main/CLI.md); [src/node/sign.ts](https://github.com/modelcontextprotocol/mcpb/blob/main/src/node/sign.ts)).
- A repo-wide grep of the `.md` and `.ts` files in the mcpb repo for quarantine, notarization, codesign, xattr, Gatekeeper, and "Developer ID" found only the `codeSigning` EKU in `sign.ts` and a test schema fixture `com.apple.darwin: { bundle_id, notarized: true }` in `test/schemas.test.ts`. The manifest `_meta` field carries "macOS bundle identifiers" (MANIFEST.md:257).
- Claude Desktop's runtime handling of quarantine or binary signing: **UNVERIFIED** (no documentation found; closed source for the app).

- Entitlements (repo files, read via GitHub): `app-entitlements.plist` sets `allow-jit`, `audio-input`, `camera`, `apple-events` (no `disable-library-validation`). `server-entitlements.plist` and `helper-plugin-entitlements.plist` set `allow-jit`, `allow-unsigned-executable-memory`, and `disable-library-validation` ([microsoft/vscode build/azure-pipelines/darwin](https://github.com/microsoft/vscode/tree/main/build/azure-pipelines/darwin)).
