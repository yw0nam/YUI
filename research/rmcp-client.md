Scope: rmcp **3.8.0** (tag `rmcp-v3.8.0`, commit `cd88056ffdc97756fbd98e5a12bbeb41758f0ce8`; the clone's HEAD is that tag; root `Cargo.toml` line 14 `version = "3.8.0"`). Companion crate: process-wrap **10.0.1** (tag `v10.0.1`, commit `ca45003a831ac125e6673b8759430e5ef33cc1db`). MCP spec read: **2026-07-28** (plus **2025-11-25** where a legacy rule is cited). Docs read: tokio **1.54.1**, tauri **2.12.5**, docs.rs rmcp **3.8.0** (`RequestHandle` page), read on **2026-10-28**. Source citations are `crates/rmcp/src/...` in the clone unless a URL is given. ## Part 1: Image content in `CallToolResult`

**Short answer.** `CallToolResult.content` is `Vec<ContentBlock>`. An image arrives as `ContentBlock::Image(ImageContent)`, which is JSON `{"type":"image","data":"<base64>","mimeType":"image/png"}`. `ImageContent.data` is a `String` holding the base64 text as received. rmcp does not decode, validate, or re-encode it. `mime_type` is a `String` that serde maps to `mimeType`.

**Evidence.**
- `crates/rmcp/src/model/content.rs:62-66`: `pub struct ImageContent { ... pub data: String, ... pub mime_type: String, ... }`. Doc comments: `/// The base64-encoded image data.` and `/// The MIME type of the image (e.g. `image/png`).` The struct is `#[serde(rename_all = "camelCase")]`.
- `crates/rmcp/src/model/content.rs:256-261`: `#[serde(tag = "type", rename_all = "snake_case")] pub enum ContentBlock { ..., Image(ImageContent), ... }`.
- `crates/rmcp/src/model.rs:4135` `pub struct CallToolResult`, and `model.rs:4150` `pub content: Vec<ContentBlock>,`.
- `crates/rmcp/src/model/content.rs:318`: `pub fn as_image(&self) -> Option<&ImageContent>`.
- Spec, `https://modelcontextprotocol.io/specification/2026-07-28/server/tools` (section "Image Content"): `{"type": "image", "data": "base64-encoded-data", "mimeType": "image/png", ...}`.
- Negative search: `grep -rn -E 'decode\(|STANDARD\.decode' --include='*.rs' crates/rmcp/src` returns decoders only in unrelated code (`transport/async_rw.rs:505`, `transport/common/mcp_headers.rs:263`, `model/request_state.rs:642`, `transport/auth/enterprise.rs`). None touches `ImageContent.data`. The only base64 encode is in `model/prompt.rs:142-182`, for prompt images.
- Inference, not tested: `data` and `mime_type` have no `#[serde(default)]`, so a result image without `mimeType` should fail to deserialize.

## Part 2: `RequestHandle::cancel` and drop behavior

**Short answer.** `cancel` sends one `notifications/cancelled` with `requestId` = the handle's request id, the `reason` you pass, and no `_meta`. It does not wait for a response, and it consumes the handle. It has no check that refuses `initialize`. **Dropping a `RequestHandle` sends nothing.** Cancel-on-drop exists only for the high-level helper futures (`call_tool`, `call_tool_once`, and several list/get helpers), through a private guard, and that send is best-effort.

**Signatures (quoted).**
- `crates/rmcp/src/service.rs:529`: `pub struct RequestHandle<R: ServiceRole> { pub rx: ..., pub options: PeerRequestOptions, pub peer: Peer<R>, pub id: RequestId, pub progress_token: ProgressToken, ... }`.
- `service.rs:653`: `pub async fn cancel(self, reason: Option<String>) -> Result<(), ServiceError>`.
- `service.rs:840-844`: `pub async fn send_cancellable_request(&self, request: R::Req, options: PeerRequestOptions) -> Result<RequestHandle<R>, ServiceError>`. This is how a caller obtains a handle for `tools/call`. `RunningService` derefs to `Peer` (`service.rs:1052-1058`).
- docs.rs `https://docs.rs/rmcp/latest/rmcp/service/struct.RequestHandle.html` (rmcp 3.8.0): `pub async fn cancel(self, reason: Option<String>) -> Result<(), ServiceError>`. The page has no text about dropping a handle.

**What `cancel` sends** (`service.rs:653-672`): a `CancelledNotification` with `request_id: Some(self.id)`, `reason`, `meta: None`, sent through `self.peer.send_notification(...)`. `send_notification` (`service.rs:822-832`) awaits the transport write, not a response. Negative: `cancel` contains no `initialize` check (read `service.rs:653-672`).

**Drop behavior.**
- Negative search: `grep -rn 'Drop for' --include='*.rs' crates/rmcp/src` lists 10 impls (`service.rs:1161` RunningService, `child_process.rs:45`, `worker.rs:119`, `service/client.rs:467`, `:503`, `:686`, `handler/client/progress.rs:90`, and others). None is for `RequestHandle`. `grep -rn 'RequestHandle' crates/rmcp/src` shows only definitions and constructors (`service.rs:529, 538, 844, 852, 862, 917, 933`).
- So dropping a handle drops its `oneshot` receiver. The service loop ignores the failed send (`let _ = responder.send(response);`, `service.rs:1467`). No cancel reaches the server, so the server keeps working.
- Helper futures do cancel on drop. `service/client.rs:486-515` defines `AbandonedRequestGuard`, whose `Drop` calls `try_cancel_request`. `service/client.rs:1457-1470` `send_request_cancel_on_drop` arms it. `call_tool_once` (`service/client.rs:1472-1480`) and `call_tool` (`service/client.rs:2061`, which calls `call_tool_once`) use that path. The `RunningService::call_tool` at `service/client.rs:2061` is therefore cancel-on-drop.
- `try_cancel_request` (`service.rs:971-986`) uses `self.tx.try_send(...)` and discards the result (`let _ =`). If the channel is full the cancel is dropped silently.
- Spec: 2026-07-28 `basic/transports/stdio` (section "Cancellation") says "the client **MUST** send a `notifications/cancelled` notification referencing the request's ID." So an explicit `cancel` matches the spec. A dropped handle does not. The 2025-11-25 cancellation page says "The `initialize` request **MUST NOT** be cancelled by clients." rmcp's `RequestHandle::cancel` would allow it. The guard comment at `service/client.rs:1454-1456` says "Never route `initialize` or `server/discover` through here."

## Part 3: `_meta` (`protocolVersion`, `clientCapabilities`) and version negotiation

**Short answer.**
- **Default `serve` does not send these keys.** `serve_client` uses `ClientLifecycleMode::Initialize` (`service/client.rs:755-770`), which performs a legacy `initialize`. Against a 2025-11-25 server, rmcp sends no per-request `_meta` at all.
- **The keys are sent only after a modern lifecycle is established**, via `Peer::set_client_request_metadata`. `service.rs:871-876` copies `protocolVersion`, `clientInfo`, and `clientCapabilities` into every outgoing request when that metadata is set. It is set in three cases:
  1. `discover_startup` succeeds (`service/client.rs:1081-1086`). The probe itself carries the same keys (`service/client.rs:1040-1046`).
  2. `legacy_startup` gets an `initialize` response whose version has no handshake (`service/client.rs:997-1003`).
  3. `configure_direct_peer` runs for a direct peer with no handshake (`service/client.rs:303-316`).
- **Spec.** `https://modelcontextprotocol.io/specification/2026-07-28/basic/index#meta` says the per-request fields `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` are required, and "fields marked as required **MUST** be included on every request." Modern servers reject requests missing them (rmcp server: `handler/server.rs:78-106`, `model/meta.rs:518-530`). Legacy servers have no such requirement.
- **Default `initialize` version.** `InitializeRequestParams::default()` sets `protocol_version: ProtocolVersion::default()` (`model.rs:1602-1609`). `impl Default for ProtocolVersion` returns `Self::LATEST` (`model.rs:154-157`), and `LATEST = V_2026_07_28` (`model.rs:167, 174`). The default `ClientHandler::get_info` returns `ClientConfig::default()` (`handler/client.rs:277-279`). So unless you override `get_info`, a default `initialize` declares `2026-07-28`.
- **Server-returned version is not checked.** `legacy_startup` (`service/client.rs:951-1011`) stores the server's `initialize_result.protocol_version` and only tests `has_initialize()` (line 997). Negative search: `grep -n 'protocol_version' crates/rmcp/src/service/client.rs` returns lines 281-356, 882, 898, 997-999, 1070-1082, 2354. None compares a server-returned version inside `legacy_startup`. The session proceeds with whatever version the server returns.

**Negotiation by mode** (`ClientLifecycleMode`, `service/client.rs:704-718`):
- `Initialize` (default): see above. Accepts any returned version.
- `Discover { preferred_versions }`: `discover_startup` (`service/client.rs:1019-1110`) selects the first caller-preferred version that the server lists in `supported_versions`, via `select_protocol_version` (`service/client.rs:281-291`). If none matches, it returns `NoCompatibleProtocolVersion`. An empty list returns `NoPreferredProtocolVersion` (`:1032`). On `UNSUPPORTED_PROTOCOL_VERSION` it retries with the server's `supported` list. A legacy reply is an error (`service/client.rs:857`), so this mode does not fall back.
- `Auto { preferred_versions, legacy_version }`: discover with a 10 s timeout (`DEFAULT_AUTO_DISCOVER_TIMEOUT`, `service/client.rs:719`). It falls back to `initialize` on a non-modern JSON-RPC error or on timeout (`service/client.rs:861-894`). Only `MISSING_REQUIRED_CLIENT_CAPABILITY` and `HEADER_MISMATCH` count as modern rejection codes (`service/client.rs:923-929`).
- **Client default list.** The client has no default preferred list. The caller supplies it. `KNOWN_VERSIONS` (`model.rs:202-208`: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28) is the server-side default (`service.rs:291-292`).
- Spec: the stdio backward-compatibility section says probe with `server/discover` and fall back on "any error that is not a recognized modern error" (2026-07-28 `basic/transports/stdio`, section "Backward Compatibility"). `Auto` matches that wording. The probe timeout matches "does not respond within a reasonable timeout."

## Part 4: `TokioChildProcess` limits (macOS, Windows, shutdown)

**Short answer.**
- **rmcp 3.8 applies no process wrapper.** `TokioChildProcess::new` (`child_process.rs:61-64`) calls the builder's `spawn` (`child_process.rs:150-165`). The only stdio settings are `stdin` and `stdout` piped and `stderr` inherited (`child_process.rs:127-129`). There is no `ProcessGroup`, `JobObject`, `CreationFlags`, or `KillOnDrop`. Negative search: `grep -rn -E 'ProcessGroup|JobObject|creation_flags|CREATE_NO_WINDOW|CREATE_NEW_PROCESS_GROUP|kill_on_drop|process_group|\.wrap\(' crates/rmcp/src` finds no wrap in `src`. Only test files use `kill_on_drop`.
- **Kill scope is the direct child only, unless the caller wraps.** Drop and the graceful-timeout path call `kill()` on the direct child. That is `start_kill` (process-wrap `core.rs:146-152` default `kill`), which is SIGKILL on Unix (docs.rs tokio `Child::kill`: "This is equivalent to sending a `SIGKILL` on unix platforms followed by `wait`"). **On macOS, descendants of the server are not signalled.** Example: `npx` → `node`. This is source-based inference; the runtime result was not run.
- **To kill the tree, the caller opts in.** On Unix, `ProcessGroup::leader()` (`process_group.rs:43-49`) makes `ProcessGroupChild::start_kill` send `SIGKILL` to the group via `killpg` (`process_group.rs:113-115, 174-176`). On Windows, `JobObject` (`job_object.rs:31-44`) makes `JobObjectChild::start_kill` call `terminate_job` (`job_object.rs:172-174`, `windows.rs:239-241`). `make_job_object` sets `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` when `kill_on_drop` (`windows.rs:118-156`). The wrap is applied with `CommandWrap::wrap` (`process-wrap generic_wrap.rs:86`). rmcp accepts `impl Into<CommandWrap>` (`child_process.rs:61`), so a pre-wrapped command can be passed.
- **Windows creation flags and issue #253.** Issue #253 ("The STDIO command creation flags still not working") is **closed**, fixed by PR #279 ("fix: let users decide what to wrap in child process command"), merged 2025-06-24 (issue and PR pages). The PR diff, read from `refs/pull/279/head` (commit `a3def9e21a56f5a82a22079576af444d0992d87d`, parent `1f7f4d30550129f43bcbd7f526ad89614df30b56`), removes the hardcoded `#[cfg(unix)] ProcessGroup::leader()` and `#[cfg(windows)] JobObject` from `TokioChildProcess::new`. The 3.8 source confirms it. A caller who needs no console window adds `CreationFlags(CREATE_NO_WINDOW)` via `process_wrap::tokio::CreationFlags` (`process-wrap creation_flags.rs:23-24`, re-exported `tokio.rs:15`). Process-wrap 10.0.1 documents that "registration order does not matter" (`creation_flags.rs:21-22`). The issue's workaround (commenting out `JobObject`) was for the old code.
- **Windows default console behavior at 3.8 is UNVERIFIED** (not run). See Unverified.
- **Graceful shutdown** (`child_process.rs:81-107`): close stdin (`transport.close()` drops the write half, `transport/async_rw.rs:325-329`), wait up to `MAX_WAIT_ON_DROP_SECS = 3` (`child_process.rs:10, 87`), then `kill()`. It sends **no SIGTERM**. The spec's stdio shutdown section says: close the input stream, wait, then "forcibly terminating the process ... On POSIX systems, forced termination typically escalates from `SIGTERM` to `SIGKILL`. On Windows ... `TerminateProcess` or Job Objects." rmcp matches close and wait, and skips the SIGTERM step.
- **When graceful shutdown runs.** `RunningService::close()` and `cancel()` (`service.rs:1109`, `:1154`) end the serve loop, which calls `transport.close()` (`service.rs:1795`), which calls `graceful_shutdown` (`child_process.rs:182-183`). Dropping `RunningService` only cancels its token (`service.rs:1161-1173`, which logs "RunningService dropped without explicit close()"). The close then runs later in the background task.
- **Dropping `TokioChildProcess` without close.** `ChildWithCleanup::drop` (`child_process.rs:45-57`) spawns a detached `inner.kill()`. It does not close stdin and does not wait for exit.
- **Windows shims.** `which_command` (`child_process.rs:217-224`, feature `which-command`, `Cargo.toml:187`) resolves `.cmd`/`.exe` shims. The doc comment says `npx.cmd` is not reliably found without a full path.

## Part 5: Running inside Tauri's runtime

**Short answer.** From the code, rmcp has no special incompatibility with a Tokio runtime. There are three constraints to design for.
1. **Connect needs a runtime context.** `serve_client` spawns with `tokio::spawn`: the worker at `transport/worker.rs:229` and the service task via `spawn_service_task` at `service.rs:1308-1313`. Tokio's `spawn` "Panics if called from outside of the Tokio runtime" (docs.rs `tokio::task::spawn`, tokio 1.54.1). Call `serve_client` from inside `tauri::async_runtime::spawn`, an `async` `#[tauri::command]`, or `tauri::async_runtime::block_on`. Tauri's `spawn` runs `runtime.spawn(task)` on its global runtime (`tauri crates/tauri/src/async_runtime.rs` at tag `tauri-v2.12.5`, fetched). Tauri's docs say it uses the runtime for `setup` hooks, but do not say whether a bare `tokio::spawn` works in a setup hook. Use `async_runtime::spawn` there. Status: UNVERIFIED.
2. **Drop also needs a context.** `ChildWithCleanup::drop` calls `tokio::spawn` (`child_process.rs:50`). Dropping a `TokioChildProcess` on a thread with no runtime context panics.
3. **Exit-time cleanup must be explicit.** Tauri's runtime is process-global: `RUNTIME.get_or_init(default_runtime)` (tauri source). Its docs say "you cannot drop the underlying TokioRuntime" (`https://docs.rs/tauri/latest/tauri/async_runtime/index.html`). The detached kill from Drop, and the background close after a dropped `RunningService`, may not finish before the process exits. Consequence: call `client.close().await` (`service.rs:1109-1112`) on app exit. Whether tasks are lost at exit is UNVERIFIED.
- The runtime fits the transport. Tauri's default is `TokioRuntime::new()`, and tokio documents `Runtime::new` as "the multi threaded scheduler, I/O driver, and time driver being initialized" (docs.rs tokio 1.54.1). The child pipes and the `sleep` in `graceful_shutdown` need both drivers.
- Send bound: `spawn_service_task` requires `F: Future + Send + 'static` unless the `local` feature is enabled (`service.rs:1305-1314`). The handler must therefore be `Send + 'static`.
